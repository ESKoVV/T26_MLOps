# Технологический стек курса MLOps 2026–2027

Редактируемый исходный файл к комплекту материалов курса. Актуализировано 19 октября 2026 года по 16-недельному плану РПД.

## 1. Назначение файла

Документ объясняет, какие технологии используются в курсе, какую задачу решает каждая из них и какой результат должен получить студент. Это не перечень продуктов для механического изучения: инструменты объединены в единый жизненный цикл ML-системы — от постановки задачи и версионирования данных до выпуска, наблюдаемости и реакции на инциденты.

Версии инструментов фиксируются преподавателем перед началом семестра в файлах проекта и CI. В тексте курса используются устойчивые публичные интерфейсы, а не непроверенные примеры из старых руководств.

## 3. Git и GitHub

### Git

Git хранит историю исходного кода и конфигурации. Студент должен уметь создать ветку, сделать содержательный commit, разрешить простой конфликт и связать изменение с задачей. Большие наборы данных, секреты и сгенерированные модели в Git не добавляются.

### GitHub

GitHub используется как центральная площадка командной работы. Для каждой команды создается отдельный репозиторий из общего шаблона курса.

Минимальный рабочий процесс:

1. Задача фиксируется в Issue с критериями готовности.
2. Участник создает короткоживущую ветку от актуальной `main`.
3. Изменение сопровождается тестами и документацией.
4. Открывается pull request, который связывается с Issue.
5. Другой участник выполняет review; автор отвечает на замечания.
6. CI должен завершиться успешно до слияния.
7. Выпуск отмечается тегом и GitHub Release, если это предусмотрено лабораторной.

Настройки репозитория команды:

- защищенная ветка `main`;
- запрет прямого push в `main`;
- не менее одного одобрения pull request;
- обязательное прохождение CI;
- `CODEOWNERS` либо явно назначенный reviewer;
- шаблоны Issue и pull request;
- секреты только в GitHub Actions Secrets или учебном менеджере секретов;
- журнал решений в `docs/decisions/` или ADR-файлах.

GitHub Issues и Projects применяются для планирования. Вклад студента подтверждается не числом commit, а принятыми артефактами: Issue, pull request, review, кодом, тестами, документацией и участием в разборе инцидента.

Официальная документация: [GitHub Docs](https://docs.github.com/), [GitHub Actions для Python](https://docs.github.com/en/actions/tutorials/build-and-test-code/python).

## 4. GitHub Actions и CI/CD/CT

GitHub Actions выполняет workflow из `.github/workflows/*.yml` на события `push`, `pull_request`, ручной запуск или публикацию тега.

Учебный CI включает:

- установку зафиксированных зависимостей;
- статический анализ и проверку форматирования Ruff;
- проверку контракта данных;
- запуск pytest с JUnit-отчётом;
- экспорт и проверку OpenAPI;
- обучение небольшой тестовой модели;
- smoke-тест API;
- сборку контейнерного образа с тегом по commit SHA;
- проверку зависимостей, образа и SBOM;
- публикацию отчетов и артефактов.

В ЛР8 checks `quality` и `container` обязательны для `main`; дорогая сборка зависит от успешного quality job. Workflow использует read-only permission, отменяет устаревшие runs одной ветки и сохраняет диагностические reports. Каждый студент показывает собственную пару запусков: контролируемый отказ и успешное исправление.

CD означает управляемую доставку проверенного образа в среду. CT — автоматический запуск переобучения при появлении разрешенных данных или по расписанию. В учебном проекте production-доступ не требуется: команды демонстрируют тот же процесс в изолированной среде.

Токены и пароли запрещено печатать в логах. Сторонние Actions фиксируются по проверенной версии; преподаватель обновляет их централизованно в шаблоне курса. На дату актуализации стартовый workflow использует `actions/checkout@v7`, `actions/setup-python@v7` и `actions/upload-artifact@v4`; перед семестром версии повторно сверяются с официальными release notes.

## 5. Python, данные и модель

Python — основной язык практической части. В стартовом проекте используются:

- `pandas` для чтения и преобразования табличных данных;
- `scikit-learn` для базовой модели и pipeline преобразований;
- `joblib` для учебного сохранения модели;
- `pyproject.toml` для метаданных проекта и зависимостей.

Код разделяется на подготовку данных, обучение, оценку и serving. Путь к данным, random seed, гиперпараметры и выходные артефакты задаются явно. Ноутбук может применяться для исследования, однако воспроизводимый запуск оформляется скриптом или pipeline.

## 6. pytest и Ruff

`pytest` проверяет поведение системы. В курсе используются:

- unit-тесты преобразований;
- проверки схемы и диапазонов данных;
- контрактные тесты API;
- smoke-тест загрузки модели;
- интеграционный тест короткого pipeline;
- regression-тест ключевой метрики в допустимом диапазоне.

Тест вида `assert True` не является доказательством качества. Для каждого теста должно быть понятно, какой риск он контролирует.

Ruff обеспечивает единообразие и выявляет типовые дефекты до review. Конфигурация хранится в репозитории и одинакова локально и в CI.

Документация: [pytest](https://docs.pytest.org/), [Ruff](https://docs.astral.sh/ruff/).

## 7. DVC и управление данными

DVC связывает версии данных и pipeline с Git-историей, не помещая крупные файлы в сам Git. Типовой цикл: `dvc init`, `dvc add`, описание стадий в `dvc.yaml`, воспроизведение через `dvc repro`, обмен через настроенное remote-хранилище.

Команда обязана описать:

- источник и лицензию данных;
- схему, ключи и единицы измерения;
- правила очистки и разбиения;
- контроль утечки целевой переменной;
- версию набора, использованную для модели;
- допустимость хранения персональных данных.

В публичные репозитории помещаются только разрешенные обезличенные или синтетические данные. Документация: [DVC](https://dvc.org/doc/) и [типовой DVC workflow](https://dvc.org/doc/command-reference/).

## 8. MLflow

MLflow Tracking сохраняет параметры, метрики, артефакты и связь запуска с версией кода и данных. Model Registry управляет версиями моделей. На 20 октября 2026 года для курса проверена ветка MLflow 3.16.x; в starter project закреплен диапазон `mlflow>=3.16,<4`.

В курсе применяются:

- experiment и run для каждого воспроизводимого обучения;
- логирование параметров, метрик, модели и отчета;
- signature и input example;
- зарегистрированная модель;
- aliases `candidate` и `champion` как изменяемые указатели;
- version tags `validation_status`, `source_commit`, `data_sha256`, `release_status` и `owner_team`;
- JSON release manifest с exact model version, run ID, commit, hash данных, решением и previous champion;
- smoke loading после promotion и rollback.

Устаревший процесс, основанный на стадиях `Staging`/`Production`, не используется. Автоматический quality gate и человеческий approval фиксируются отдельно. Registry использует database-backed backend; для локальной ЛР10 допускается SQLite. Alias не заменяет exact version в manifest, а rollback выполняется переназначением `champion` без переобучения и удаления истории.

Документация: [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) и [Model Registry workflow](https://mlflow.org/docs/latest/ml/model-registry/workflow/).

## 9. Docker и OCI-образ

Docker упаковывает сервис и runtime-зависимости в переносимый OCI-образ. Студент должен понимать Dockerfile, build context, слои, теги и отличие образа от контейнера.

Требования курса:

- минимальный базовый образ с фиксируемой версией;
- непривилегированный пользователь;
- отсутствие секретов и учебных данных внутри образа;
- `.dockerignore`;
- health/readiness endpoints;
- воспроизводимая установка зависимостей;
- SBOM и сканирование образа;
- тег, позволяющий связать образ с commit и версией модели.

Документация: [Docker manuals](https://docs.docker.com/) и [OCI Image Specification](https://github.com/opencontainers/image-spec).

## 10. Prefect и сравнение с Apache Airflow

Prefect является обязательным оркестратором практической части. В учебном flow отдельными задачами становятся валидация, подготовка, обучение и оценка. Параметры запуска задаются явно, ошибки не скрываются, повторный запуск не должен повреждать ранее созданные артефакты.

На дату актуализации используется Prefect 3.8.x; в `pyproject.toml` задан диапазон `prefect>=3.8,<4`. Перед семестром преподаватель повторно проверяет актуальный stable release, совместимость Python и интерфейсы flow/task. Starter flow сохраняет JSON-отчёт каждой завершённой стадии и общий summary, а retry применяется только к учебному transient-сценарию подготовки данных.

Студент должен объяснить состояние flow и task, retries, таймаут, кеширование, идемпотентность и отличие кода обработки от кода оркестрации. В доказательства ЛР9 входят код flow, параметры, журнал успешного запуска и журнал контролируемого отказа.

Airflow используется для сравнительного обзора DAG-подхода. Его установка и разработка отдельного DAG не обязательны. Ни Prefect, ни Airflow не заменяют код обработки данных, MLflow и мониторинг.

Документация: [Prefect Docs](https://docs.prefect.io/) и [Apache Airflow Documentation](https://airflow.apache.org/docs/).

## 11. FastAPI, Pydantic и Uvicorn

FastAPI предоставляет HTTP-интерфейс модели, Pydantic валидирует входные и выходные структуры, Uvicorn запускает ASGI-приложение.

Обязательные endpoints стартового проекта:

- `/healthz` — процесс работает;
- `/readyz` — модель загружена и сервис готов принимать запросы;
- `/predict` — типизированный контракт инференса;
- `/metrics` — технические метрики.

Ответ `/predict` содержит результат, версию модели и `request_id`. В логах не должны появляться исходные персональные данные или секреты.

Документация: [FastAPI](https://fastapi.tiangolo.com/) и [Pydantic](https://docs.pydantic.dev/).

## 12. Docker Compose и обзор Kubernetes

Docker Compose задаёт обязательный локальный контур: сервис предсказаний, MLflow, Prometheus и Grafana запускаются согласованными версиями и сетевыми именами. Конфигурация не содержит секретов, имеет healthcheck там, где это оправдано, и позволяет повторить демонстрацию на чистой машине.

Kubernetes рассматривается как следующий уровень эксплуатации контейнерных workload. На лекции и демонстрации используются Deployment и Service, probes, requests/limits, ConfigMap/Secret и базовый rolling update. Локальный кластер не является обязательным условием сдачи.

Минимальные требования безопасности:

- запуск не от root;
- запрет privilege escalation;
- удаление лишних Linux capabilities;
- read-only root filesystem, если приложение это допускает;
- ограничения CPU и памяти;
- readiness и liveness probes;
- секреты не хранятся в manifest открытым текстом;
- применение принципов Pod Security Standards `Baseline`/`Restricted`.

Документация: [Kubernetes Concepts](https://kubernetes.io/docs/concepts/), [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) и [Security Checklist](https://kubernetes.io/docs/concepts/security/security-checklist/).

## 13. Prometheus, Grafana и OpenTelemetry

Prometheus собирает метрики, Grafana визуализирует их и поддерживает панели/алерты. OpenTelemetry дает стандартную инструментализацию для метрик, логов и трассировок; он не является хранилищем или интерфейсом визуализации сам по себе. На 20 октября 2026 года starter project использует `prometheus-client>=0.26,<1`, Prometheus `v3.15.0` и Grafana OSS `13.2.4`.

Команда контролирует два слоя:

- сервис: частота запросов, ошибки, latency, насыщение ресурсов;
- ML: распределения признаков и предсказаний, доля отказов валидации, drift и отложенное качество.

ЛР11 реализует RED-сигналы через `http_requests_total` и `http_request_duration_seconds`, отдельную `model_info`, JSON-логи с request ID и release identity, provisioned datasource/dashboard, Prometheus recording/alert rules и runbook. Labels ограничиваются route template, method, status и контролируемой model version; request ID, raw URL, пользовательские значения, признаки и текст ошибки в labels запрещены.

Для итоговой работы задаются SLI и SLO, окно, минимум трафика, условия alert, владелец реакции и runbook. Dashboard и datasource хранятся как код. Высокая доступность процесса без корректного результата модели не считается надежностью ML-системы; drift и delayed quality отделены в ЛР12.

Документация: [Prometheus](https://prometheus.io/docs/), [Grafana](https://grafana.com/docs/), [OpenTelemetry](https://opentelemetry.io/docs/) и [observability primer](https://opentelemetry.io/docs/concepts/observability-primer/).

## 14. Drift и Evidently

Drift означает изменение распределения данных или предсказаний относительно согласованной reference-выборки. Он является сигналом для расследования, а не автоматическим доказательством деградации качества.

В лабораторной команда выбирает статистические проверки и пороги, формирует отчет, связывает алерт с runbook и определяет условия переобучения. Если используется Evidently, версия библиотеки фиксируется, поскольку интерфейсы отчетов могут изменяться.

Документация: [Evidently](https://docs.evidentlyai.com/).

## 15. Feature Store и Feast

Feature store помогает согласовать вычисление и публикацию признаков для обучения и inference. Ключевые понятия: entity, feature view, offline store, online store, event timestamp и point-in-time join.

В курсе важнее корректность времени, происхождение признака и отсутствие leakage, чем развертывание крупной платформы. Feast применяется как референсная реализация либо заменяется небольшим учебным прототипом с теми же контрактами.

Документация: [Feast](https://docs.feast.dev/).

## 16. Безопасность цепочки поставки

Команда должна уметь связать исходный commit, CI-run, образ, SBOM и версию модели. Проверяются зависимости Python и контейнерный образ. Найденная уязвимость оценивается по применимости и риску; одно число сканера не заменяет решения владельца.

Допустимые учебные инструменты выбираются преподавателем перед семестром, например Syft для SBOM и Trivy либо Grype для сканирования. Выбор конкретного продукта вторичен по отношению к проверяемому процессу.

## 17. Responsible AI и нормативные требования

Каждая команда поддерживает model card, data card и risk register. В них фиксируются назначение, ограничения, исключенные сценарии, группы риска, методы проверки, владелец и порядок остановки/отката.

Правовые требования рассматриваются применительно к сценарию проекта. Студенты не дают юридических заключений, а учатся выявлять потенциальные обязанности, собирать доказательства контроля и передавать вопрос ответственному специалисту.

Официальные ориентиры: [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) и [European Commission — AI regulatory framework](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai).

## 18. LLMOps

Модуль LLMOps расширяет знакомый процесс на системы с генеративной моделью. Версионируются prompt, системные инструкции, параметры, модель/провайдер, инструменты и набор eval-кейсов.

Оценка включает не только средний score, но и проверку критических сценариев: фактическая корректность, соблюдение формата, устойчивость к prompt injection, утечка данных, стоимость и latency. Для запросов и ответов действует политика минимизации и маскирования чувствительных данных.

Допустимые инструменты: MLflow GenAI либо эквивалентный стек трассировки и eval. Документация: [MLflow GenAI](https://mlflow.org/docs/latest/genai/).

## 22. Drift и отложенное качество

Обязательная реализация ЛР12 использует pandas и NumPy, version-controlled policy и JSON-отчёт.
Числовой PSI строит границы только по reference-окну, категориальный PSI учитывает объединение
категорий. Для каждой метрики фиксируются reference/current окна, минимальный объём, warning и
alert threshold. Coverage рассчитывается среди прогнозов, для которых к `as_of` уже ожидается
фактическая метка; свежие прогнозы не ухудшают знаменатель.

Evidently допускается как расширение (`evidently>=0.7.23,<0.8` на 20 октября 2026 года), но
его интерактивный HTML не заменяет машинно-читаемый JSON, policy, тесты и объяснение метода.
Drift является сигналом расследования, а не самостоятельным основанием для retraining. Решение
о candidate требует зрелых labels, достаточного coverage, деградации качества и review.

## 23. Point-in-time признаки и Feature Store

Обязательный путь ЛР13 реализован на pandas и сравнивает намеренно наивный latest join с
point-in-time join. Контракт фиксирует entity key, `event_time`, `feature_time`, `available_time`,
TTL, список признаков и владельца. Для каждой строки обучения выбирается последнее значение,
которое не только относится к прошлому, но и фактически было доступно в момент прогноза.

Feast рассматривается как демонстрационный вариант, а не условие допуска. На 20 октября 2026 года
фиксируется `feast>=0.67,<0.68` (stable 0.67.0). Feature view содержит source, entity, schema, TTL,
validation и tags; feature service связывает набор признаков с версией модели. Historical retrieval
используется для training/batch scoring, online retrieval — для текущего inference. Скриншот UI не
заменяет definitions-as-code, тест point-in-time корректности и audit JSON.

## 24. Документация, безопасность и Responsible ML

ЛР14 переводит документацию в проверяемый release evidence. `docs/model-card.md` фиксирует
назначение, недопустимые сценарии, модель и данные, качество, групповые метрики, ограничения,
мониторинг, безопасность, надзор человека и владельца. `docs/data-card.md` дополняется сведениями о
происхождении, правах, хранении и производных артефактах. Обязательные заголовки model card
проверяются в CI модулем `mlops_flight_delay.governance`.

Групповой аудит использует общую policy в JSON: сегмент, порог классификации, минимальный размер
группы, минимальный общий F1 и максимально допустимый F1 gap. Малые группы подавляются, а отсутствие
двух достаточных групп переводит результат в `review`. Учебный `IsWeekend` демонстрирует механику и
не объявляется защищённым атрибутом или доказательством справедливости.

Security evidence включает `SECURITY.md`, threat model, allowlist логирования, минимальные GitHub
Actions permissions, secret scanning/push protection и порядок ротации секрета. Проверка сторонних
компонентов опирается на фактический SBOM/lock и официальный источник лицензии; неизвестная лицензия
блокирует release. Управление рисками соотносится с функциями NIST AI RMF: Govern, Map, Measure,
Manage, но framework применяется контекстно, а не как механический чек-лист.

## 25. Производительность, capacity и обзор LLMOps

ЛР15 использует стандартную библиотеку Python для закрытого steady/burst профиля и сохраняет сырые
latency каждого запроса. `mlops_flight_delay.capacity` воспроизводимо рассчитывает nearest-rank
p50/p95, throughput, error rate и recovery time, сравнивает их с `capacity/load_policy.json` и
формирует `keep_baseline` либо `investigate_then_scale`. Live load не является стабильным CI gate;
в CI проверяется детерминированный sample, а реальные прогоны прикладываются к PR как artifacts.

Kubernetes остаётся обзорным контуром. Deployment дополнен rolling strategy, startup/readiness/
liveness probes и immutable version tag; HPA использует `autoscaling/v2`, resource CPU target и
scale-down stabilization, PDB — `policy/v1`. CPU HPA не интерпретируется как прямой контроллер p95:
сначала подтверждается bottleneck. Кластер и metrics-server не требуются для допуска.

LLMOps рассматривается через version-controlled `llmops/eval_cases.json`: format, refusal,
prompt-injection и grounding cases. Обсуждаются prompt/model/provider/tool/retrieval versions,
tracing, token usage, latency, deterministic/model/human scorers и privacy. Внешний API и ключ не
требуются. Для демонстрации допустимы MLflow GenAI Tracing и `mlflow.genai.evaluate()`; они не
смешиваются с `mlflow.models.evaluate()` классического ML.

## 26. Итоговый release manifest и проверяемый rollback

ЛР16 связывает full source commit, data/feature contracts, MLflow run, exact model version, alias
`champion`, immutable image ref, OpenAPI version, CI run, release gates, approvals и rollback.
`mlops_flight_delay.release` строит manifest из `release_spec`, вычисляет SHA-256 каждого evidence и
повторно проверяет hashes. Изменение отчёта после approval обнаруживается командой `verify`.

Manifest не может стать `ready` без успешного CI и независимого reviewer. Gate со статусом
`accepted_with_investigation` требует причины, владельца и срока пересмотра; итоговый status становится
`ready_with_exception`. Учебный example честно остаётся `draft`. Плавающий image tag `latest`
запрещён; используется digest либо full-commit tag при политике неизменяемости registry.

Rollback рассматривается как отдельное управляемое изменение: exact previous model version и image,
причина, approver, timestamps, smoke/readiness после возврата и фиксация итогового состояния.
GitHub artifact attestations допускаются как расширение provenance. Они связывают artifact с build,
но не заменяют tests, security review, качество модели и решение о выпуске.
