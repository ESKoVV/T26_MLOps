# Правила командной работы

## Схема веток team-3

1. `ESKoVV/T26_MLOps:main` — интеграционная ветка команды. Прямой push запрещён.
2. На каждого участника есть ветка `student-02` … `student-05` (см. `docs/team-roles.md`).
3. Участник делает fork своей ветки, работает в `main` своего fork-а и открывает PR
   `STUDENT_LOGIN:main` → `ESKoVV:student-XX`. Тимлид работает в ветке задачи и открывает PR в `student-02`.
4. После review тимлид открывает PR `student-XX` → `main`.
5. ЛР1 и ЛР16: PR `ESKoVV:main` → `Irina-64:team-3`. ЛР2–ЛР15: в СКИФ — ссылка на `main` после интеграции.
6. Каждая принятая ЛР фиксируется аннотированным tag `lrN-v1` на commit с успешным CI.

## Общие правила

1. Каждое изменение начинается с issue, содержащей результат и критерии приемки.
2. Ветка создается от актуального `main` и именуется по назначению, например `docs/issue-12-setup`.
3. Pull request ссылается на issue и содержит способ проверки.
4. Автор не утверждает собственное изменение. Требуется содержательное review другого участника.
5. Merge разрешен после успешных обязательных checks `quality` и `container`, содержательного review и разрешения обсуждений.
6. Прямой push и force push в `main` запрещены командным процессом.
7. Секреты, `.env`, локальное окружение, модели и неразрешенные данные не добавляются в Git.
8. Для каждой ЛР участники заполняют индивидуальные evidence cards.
9. История намеренно неуспешного CI-run сохраняется: запрещено удалять ветку или переписывать историю до индивидуальной защиты ЛР8.
10. Повторный запуск без изменения кода не считается исправлением; участник указывает корневую причину и исправляющий commit.

## Рекомендуемые правила ветки `main`

- pull request обязателен;
- требуется минимум одно одобрение участника, который не является автором;
- обсуждения должны быть разрешены;
- обязательны уникально названные checks `quality` и `container`;
- прямой push, force push и удаление ветки `main` запрещены;
- администратор не обходит правила во время учебной приёмки.

Если настройки репозитория допускают ruleset, команда прикладывает ссылку на него или экспорт/скриншот настроек. Секреты и персональные данные в доказательства не включаются.

Если тариф GitHub не позволяет технически применить часть правил ветки, команда сохраняет те же требования как обязательный процесс и демонстрирует их соблюдение по истории pull request.
