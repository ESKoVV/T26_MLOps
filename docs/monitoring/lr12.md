# ЛР12 Drift и отложенное качество модели

Модель: champion из ЛР10 (bundle `models/lr10-a.joblib`, RF 120 деревьев, depth 8, обучена на BTS v2 до 2026-02-05).
Политика: `monitoring/drift_policy_bts.json` (`policy_version 1.0.0-team-3-bts`). Учебная `drift_policy.json` с
порогами ROC AUC 0.7 и F1 0.6 рассчитана на синтетический пример; для реальной модели с validation ROC AUC 0.576
она давала бы постоянный `quality_breach`, поэтому команда завела отдельную политику:

| Параметр | Значение | Почему |
|---|---|---|
| `minimum_window_rows` | 500 | на меньшем окне PSI по 24 часам неустойчив |
| `psi_warning` / `psi_alert` | 0.1 / 0.25 | общепринятые границы PSI |
| `expected_label_delay_hours` | 24 | фактическая задержка прибытия известна в тот же день; запас до суток |
| `minimum_label_coverage` | 0.9 | ниже — метрика смещена в сторону рейсов, по которым метка пришла быстрее |
| `minimum_roc_auc` | 0.58 | чуть выше validation 0.576 из ЛР4: заметное ухудшение = расследование |
| `minimum_f1` | 0.0 | при пороге 0.5 и доле задержек 0.15–0.26 F1 = 0 у любой версии (ЛР4); проверка F1 включится после выбора порога |
| `automatic_retraining` | false | drift сам по себе не повод переобучать |

## Окна и журналы

Сборка — `scripts/build_monitoring_window.py` (CSV в `data/monitoring/bts/`, в Git не хранятся):

- reference — признаки периода train: 2026-01-01 — 2026-02-05, 27 436 рейсов;
- current — 2026-02-17 — 2026-02-28 (период test), 9 651 рейс;
- prediction log — `request_id` = дата-перевозчик-рейс-час, `event_time` = плановый вылет − 60 мин, вероятность champion;
- label log — `ArrDelay` с `label_time` = вылет + 6 ч. BTS не даёт часовой пояс: время записано как UTC, важен только сдвиг.

```bash
python scripts/build_monitoring_window.py data/bts/atl_2026.csv models/lr10-a.joblib data/monitoring/bts/baseline \
  --reference-end 2026-02-05 --current-start 2026-02-17 --current-end 2026-02-28
python -m mlops_flight_delay.monitoring --reference data/monitoring/bts/baseline/reference.csv \
  --current data/monitoring/bts/baseline/current.csv --predictions data/monitoring/bts/baseline/predictions.csv \
  --labels data/monitoring/bts/baseline/labels.csv --policy monitoring/drift_policy_bts.json \
  --as-of 2026-03-01T12:00:00Z --output reports/monitoring/lr12-bts-baseline.json
```

## Результаты (as-of 2026-03-01T12:00Z)

| Отчёт | Сценарий | PSI DepHour | PSI IsWeekend | Drift | Coverage | ROC AUC | Решение |
|---|---|---:|---:|---|---:|---:|---|
| `reports/monitoring/lr12-bts-baseline.json` | реальное окно | 0.0039 | 0.0009 | ok | 1.000 (9 269 зрелых) | 0.645 | `no_action` |
| `reports/monitoring/lr12-bts-weekend-shift.json` | current = только выходные | 0.0051 | 17.15 | alert | 1.000 | 0.668 | `investigate` |
| `reports/monitoring/lr12-bts-late-labels.json` | 20 % меток не пришли | 0.0039 | 0.0009 | ok | 0.800 | — | `hold` |

Выводы:

- На реальном окне расписание ATL стабильно — drift нет, качество по зрелым меткам (0.645) выше порога.
- Окно из одних выходных даёт огромный PSI по `IsWeekend`, но качество не падает: решение — расследовать
  состав трафика, а не переобучать. Это и есть правило «drift без деградации → investigate».
- При coverage 0.80 метрики не считаются: оставшиеся 80 % могут быть смещённой выборкой. Решение `hold`.
- Из 9 651 прогноза зрелыми к as-of были 9 269: рейсы позже cutoff (вылет после 2026-02-28 12:00) ещё ждут метку.
