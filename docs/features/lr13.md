# ЛР13 Point-in-time признаки и Feature Store

Признаки перевозчика из фрагмента BTS (`scripts/build_feature_history.py`), контракт `features/feature_contract_bts.json`:

| Поле | Смысл |
|---|---|
| entity key `Carrier` | IATA-код перевозчика |
| `trailing_delay_rate` | доля вылетов перевозчика из ATL с `ArrDelay >= 15` за день D |
| `flights_last_24h` | число таких вылетов за день D |
| `feature_time` | D+1 00:00 — день закрыт, агрегат относится к нему |
| `available_time` | D+1 06:00 — ночной batch-расчёт; раньше признак прочитать нельзя |
| `event_time` | плановый вылет − 60 мин (момент прогноза) |
| TTL | 48 ч; `maximum_missing_rate` 0.01 |

Все времена записаны как UTC; BTS даёт местное время ATL, поэтому важны только относительные сдвиги.

## Аудит на окне 2026-02-17 — 2026-02-28 (9 651 рейс, 12 перевозчиков, 705 строк истории)

```bash
python scripts/build_feature_history.py data/bts/atl_2026.csv data/features/bts --event-start 2026-02-17 --event-end 2026-02-28
python -m mlops_flight_delay.features --entities data/features/bts/entities.csv --history data/features/bts/history.csv \
  --contract features/feature_contract_bts.json --output-dir reports/features/lr13-bts
```

`reports/features/lr13-bts/audit.json`: naive leakage — 9 651 строка (все), point-in-time leakage — 0,
изменилось относительно naive — 9 591, coverage 1.0, максимальный возраст признака 29 ч, статус `pass`.
29 ч — это прогноз в 04:00 (вылет в 05:00): данные за вчера станут доступны только в 06:00, поэтому берётся позавчерашний день.

## Влияние утечки на метрику

ROC AUC самого признака `trailing_delay_rate` как оценки задержки на том же окне:

| Join | Что попадает в строку | ROC AUC |
|---|---|---:|
| point-in-time | последний доступный к прогнозу день | **0.581** |
| same-day (утечка) | агрегат дня самого рейса, включая его собственный исход | 0.683 |
| naive latest | последний день истории (28 февраля) для всех рейсов | 0.517 |

Same-day join выглядит на 0.10 лучше, но эти данные к моменту прогноза не существуют: модель, обученная так, в
эксплуатации покажет около 0.58. Naive latest-join и утекает, и вредит — один и тот же «будущий» день на всё окно.

## Найденный дефект

Контракт объявлял `maximum_missing_rate`, но аудит его не проверял и ставил `pass` при любом покрытии; CLI всегда
завершался кодом 0. Теперь в аудите есть `missing_rate`, список `failures` (`point_in_time_leakage`,
`missing_rate_above_contract`) и ненулевой код при `fail` — CI-шаг «Audit point-in-time feature join» стал gate.

Feast: определения в `feature_repo/` остаются демонстрационными; historical retrieval в Feast выполняет тот же
point-in-time join по `event_timestamp` и TTL. Локальный Feast в работе не запускался (необязательная часть).
