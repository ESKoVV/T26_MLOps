# План производительности и масштабирования

## Контекст

Учебный API обслуживает синтетические запросы прогноза задержки. Цель ЛР15 — доказать измерением,
что выбранная конфигурация выдерживает steady и burst профиль, а после контролируемого нарушения
готовности возвращается в работу в пределах policy.

## Гипотеза и SLO

Baseline: две replicas, CPU request 100m, limit 500m. Проверяются p95, error rate, throughput и
recovery time. Клиентские 4xx из намеренно невалидных запросов анализируются отдельно и не должны
выдаваться за серверную деградацию.

## Протокол

1. Зафиксировать commit, image tag/digest, модель, машину/кластер и policy.
2. Выполнить warm-up и не включать его в итоговую статистику.
3. Повторить steady и burst не менее трёх раз; сохранить сырые latency и status.
4. Во время burst сопоставить p95 с CPU, memory, saturation и очередью.
5. Провести контролируемый restart/unready drill и измерить время до трёх успешных readiness checks.
6. Изменять за один эксперимент только один фактор.

## Решение

Один высокий p95 не доказывает нехватку replicas. Сначала исключаются client bottleneck, cold start,
I/O, lock, serialization и неверная probe. Масштабирование принимается только после подтверждения
bottleneck и с оценкой стоимости. HPA в `k8s/hpa.yaml` — демонстрационный manifest; локальный
Kubernetes не является условием допуска.

## Bottleneck

С одним worker пропускная способность на burst **падает** (≈ 95 rps против ≈ 155 на steady), а p50 растёт в 7 раз:
запросы стоят в очереди. `/predict` — синхронный обработчик, `predict_proba` у RandomForest держит GIL, поэтому
потоки одного процесса не работают параллельно. Подтверждение — эксперименты, где меняется один фактор:

- второй процесс (2 worker) — burst p95 0.19 → 0.06 с, rps ×2.8: узкое место — CPU одного процесса;
- модель вдвое меньше — p95 0.19 → 0.11 с: стоимость одного прогноза тоже значима, но меньше.

## Решение

- **Принято:** baseline 2 replicas (`baseline_replicas` policy, `k8s/deployment.yaml`), по одному worker на pod,
  CPU request 500m / limit 1. Текущий профиль проходит SLO с запасом (burst p95 0.19 с при лимите 0.45 с).
- **Альтернатива** — заменить модель на v2 (60 деревьев): тоже ускоряет, но меняет качество (test ROC AUC 0.6311 против
  0.6313) и требует нового выпуска; не нужна, пока SLO выполняется.
- **Стоимость** (учебная, условные единицы, 0.04 за replica-час): 2 replicas — 58.4 в месяц; максимум HPA 6 replicas — 175.2.
- **Rollback trigger:** после изменения числа replicas или модели burst p95 > 0.45 с либо error rate > 2 % в двух
  профилях подряд → возврат к предыдущему manifest / alias `champion`.

## Review Kubernetes и LLMOps

`k8s/deployment.yaml` исправлен:

1. Образ был `flight-delay-api:1.1.0` — изменяемый tag с другим именем, чем образ из CI. Теперь ссылка по digest
   `mlops-flight-delay@sha256:…`, который фиксируется при выпуске.
2. `readOnlyRootFilesystem: true` без записываемого `/tmp`: Python и uvicorn пишут временные файлы. Добавлен `emptyDir`
   (memory, 64Mi), как tmpfs в `compose.yaml`.
3. CPU request 100m при измеренном потреблении около одного ядра: HPA с целью 60 % срабатывал бы уже при 60m.
   Request поднят до 500m.

HPA (2–6 replicas, CPU 60 %, быстрый scale-up, scale-down со стабилизацией 300 с) и PDB (`minAvailable: 1`) согласованы
с политикой. `llmops/eval_cases.json`: 4 кейса — формат JSON, отказ выдавать секрет, prompt injection, фактическая
точность по курсу. Не хватает кейса на «уверенную выдумку»: вопрос о несуществующей метрике курса, где правильный
ответ — признать отсутствие. Внешняя LLM не вызывалась.
